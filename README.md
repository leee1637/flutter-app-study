# Warehouse App

Учёт складского инструмента: сотрудник сканирует QR-ярлык — товар закрепляется
за ним, повторное сканирование возвращает его. Работает офлайн, синхронизируется
с облаком при появлении сети.

## Что умеет

| Роль | Возможности |
| --- | --- |
| `user` | вход/регистрация, список товаров, поиск, сканирование QR, взятие и возврат товаров |
| `admin` | всё вышеперечисленное + добавление товаров с фото и генерацией QR |

## Стек

- Flutter 3.44 / Dart 3.12, Material 3
- Riverpod 2 — состояние и внедрение зависимостей
- GoRouter — маршрутизация и проверка доступа
- Firebase Auth (Email/Password) + Cloud Firestore — облако
- SQLite (`sqflite`) — локальный кэш и журнал операций
- `mobile_scanner` — камера, `qr_flutter` — генерация ярлыков
- `imgbb` — хостинг фото товаров

## Настройка Firebase

Приложение уже настроено на проект `dz11-1c536` (см. `lib/firebase_options.dart`).
Для работы нужно включить два сервиса.

### 1. Аутентификация

`Authentication` → `Sign-in method` → раздел **Email/Password** → включить.

> По умол Email/Password выключен. Пока переключатель не включён, регистрация
> падает с ошибкой `auth/operation-not-allowed`.

### 2. Firestore

`Firestore Database` → `Create database` → режим **Production mode**.

Затем `Firestore Database` → `Rules` → вставить содержимое `firestore.rules` →
**Publish**. До публикации правил все запросы будут отклоняться, потому что
значение `test_mode` по умолчанию запрещает любой доступ.

Либо из каталога проекта:

```bash
firebase deploy --only firestore:rules
```

## Где смотреть пользователей и пароли

`Authentication` → `Users` — список всех, кто зарегистрировался. По умолчанию
скрыты только часть email и UID; нажмите на строку, чтобы открыть карточку.

**Пароля в консоли нет и посмотреть его нельзя.** Firebase Auth не хранит пароль
в открытом виде — он хранит только хеш. Забытый пароль можно только сбросить:
`Authentication` → `Users` → выбрать пользователя → `Reset password`. Приложение
уже умеет слать письмо со ссылкой сброса (экран входа → «Забыли пароль?»).

Что можно увидеть, а что нет:

| Что | Где посмотреть |
| --- | --- |
| Email и UID пользователя | `Authentication` → `Users` |
| Роль (`admin` / `user`) | `Firestore` → коллекция `users` → документ с этим UID |
| Товары и их статусы | `Firestore` → коллекция `products` |
| Пароль в открытом виде | **недоступен нигде** |
| Логи входа | `Authentication` → `Users` → `Logs` |

`apiKey` в `lib/firebase_options.dart` — публичный идентификатор проекта, он
служит только для идентификации клиента и паролем не является. Секретным
ключом считается Service Account (JSON), и он в проекте не используется.

## Роли

Первый зарегистрировавшийся пользователь получает роль `admin`, остальные —
`user`. Логика в `FirebaseAuthRepository` + флаг
`AppConstants.firstRegisteredUserIsAdmin`.

Это сделано на клиенте, поэтому роль назначается по результату запроса
«есть ли в базе хоть один пользователь». Два человека, зарегистрировавшиеся
одновременно, теоретически могут получить `admin` оба. Для боевого проекта
роль выдаётся через Firebase Custom Claims (Admin SDK) и проверяется в
Security Rules. Для учебной работы текущей схемы достаточно; чтобы завести
первого админа вручную, поставьте в константе `false` и отредактируйте
документ в Firestore.

## Архитектура

```
presentation/   экраны, виджеты, провайдеры Riverpod
data/
  local/        DatabaseHelper + DAO поверх SQLite
  remote/       FirebaseProductRepository, FirebaseAuthRepository
  repositories/ ProductRepository, HybridProductRepository
  sync/         SyncManager (push/pull)
core/           константы, провайдеры зависимостей, утилиты
```

`HybridProductRepository` — единственный репозиторий, с которым работают
экраны. Он всегда сначала пишет в SQLite, а затем, если есть сеть,
дублирует операцию в Firestore. Поэтому интерфейс не зависит от наличия сети,
а после её восстановления данные уходят в облако при следующей синхронизации.

### Разделение ответственности

Бизнес-правила живут в репозиториях, а не только в UI:

- взять товар может только тот, кому он свободен;
- вернуть товар может только тот, кто его взял (`LocalProductRepository`),
  в облаке то же обеспечивает транзакция (`FirebaseProductRepository`).

Проверку в UI продублировано намеренно, но правило хранится в репозитории —
иначе его можно обойти, выключив интернет.

## Схема данных

Firestore:

- `users/{uid}` — `name`, `email`, `role`, `createdAt`
- `products/{id}` — `name`, `description`, `imageUrl`, `status`,
  `takenBy`, `takenAt`

SQLite (`DatabaseHelper`, версия схемы 3):

- `products` — кэш товаров (`taken_by`, `taken_at`)
- `users` — кэз пользователей для имён
- `transactions` — журнал: кто, когда, взял или вернул

## Формат QR

В QR кладётся **не** JSON, а ссылка на фото с идентификатором в
query-параметре:

```
https://i.ibb.co/xxx/photo.jpg?product_id=<uuid>
```

Так ярлык остаётся полезным вне приложения: обычная камера телефона откроет
его в браузере и покажет фото товара.

`QrPayload.tryParse` умеет разбирать и устаревшие форматы — старые ссылки
Firebase Storage (`products%2F<id>.jpg`), deep-link `/qr/<id>`, JSON и голый
идентификатор, — чтобы наклеенные ранее ярлыки продолжали работать.

Без сети публичной ссылки на фото нет, поэтому ярлык имеет вид
`product://<id>` и открывается только в этом приложении. Такой товар
помечается в SQLite идентификатором с префиксом `local_`, а при синхронизации
ему выдаётся постоянный UUID.

## Ограничения

- Хранить и раздавать фото через imgbb — учебное решение: ключ API вшит в код,
  для продакшена нужны Firebase Storage и серверная прокси-загрузка.
- Проверка прав сделана на клиенте. `firestore.rules` закрывают запись
  `users` от посторонних, но правило «взять/вернуть может только владелец»
  на сервере не продублировано.
- Синхронизация запускается при старте приложения и по подписке на снапшоты
  товаров; отдельного кнопочного триггера нет.
- Экран истории операций не сделан, хотя журнал `transactions` уже пишется.
